# Taco Hunt Delegation Plan

This board follows the specification in docs/build-spec.md and the repository's current state. The landing page, the initial schema, basic API reads, and the mobile list/detail screens already exist. The ngrok tunnel is a temporary view of the landing page, not a production deployment.

## Blocking rule

- A task becomes **free** when all its dependencies are closed and its input contract is agreed.
- Each worker is an independent Codex task/session, with its own history and worktree; it is not delegated as a subagent of the orchestrator's thread. Each worker modifies its own area; coordination integrates shared package.json files, pnpm-lock.yaml, root routes, and migrations that affect multiple modules.
- T00 sets a versioned baseline and the current read contract. After that, three agents can work in parallel: T01, T02, and T03. Coordination can advance T04.
- **UI first (P2.7 onward):** design/UI tasks block every other task; the API is built after the UI and shaped by it. See the UI-first rule in P2.7.
- **Final closure:** T14 stays blocked until T01–T13 are closed and must cover data from T18–T20. T15 stays blocked until T14 and T17–T24 are closed — T24 (Maps/Places cost and security controls) is the candidate most at risk of lagging and should be assigned as soon as T17 and T21 close. T16 additionally requires the external launch inputs. A task being free means it can start; opening the final closure requires it to be finished.

## P2.7: first hands-on owner test follow-up (added 2026-09-29)

The owner tested the app in Expo Go against the local API and Supabase and reported bugs and product gaps. Design items from the same test (discoverability of "add a taquería", minimized header search, empty-app feeling, photo gallery, profile screen, avatars) are specified in `docs/design-owner-feedback.md` and are built first, as Phase A (see the UI-first rule below) (owner-reviewed 2026-09-29; public canvas <https://claude.ai/artifact/9AVKB3JQW7j3UGijkxiUEv>). Read it before any P2.7 mobile task; its task-mapping table says which section each task implements and lists design sections that have no task yet. None of these block T14–T16, but T37 and T40 add new personal data (photos, avatars) that T15's account-deletion pass must cover.

Verified root causes (2026-09-29):

- **Reviews cannot be posted (T31).** `POST /v1/reviews` returns 503 for every user. `apps/api/src/reviews/reviews.controller.ts` locks with `for share of st,s,tt`; row locks need UPDATE privilege and `taco_hunt_api` only has SELECT on `taco_types`, so Postgres raises `permission denied for table taco_types`. Introduced in T08, not by the T02 API swap.
- **Sign-up gives no feedback (T32).** Local Supabase has `enable_confirmations = false`, so `signUp` returns a session; `AuthScreen` only shows a message when there is no session and never navigates (sign-in doesn't navigate either).
- **Sign-up display name is dropped (T40).** The API only inserts `profiles.id`; nothing reads `user_metadata.display_name`.
- **No review photo upload in mobile (T36).** T11's API exists, but the mobile form never sends `photoUploadId`; `photoUrl` is always `null`.
- **Map hides stands by area (T33/T34).** Area chips define the query bbox with `limit: 30`, and the map only reloads on chip change, not on pan.
- **No path from `import_candidates` to `spots` (T42), and no mobile UI for taco-type proposals (T44)** even though `POST /v1/taco-proposals` and admin approval exist.

Owner decisions (2026-09-29):

- **Seed source:** web articles, guides, and social media, researched manually or with web search (no scrapers — social network terms forbid automated extraction). Only facts are taken (name, neighborhood, address); no copied text, photos, ratings, menus, or hours. `source_type=web_research`, source URL in `source_ref`. Require one source from the last 12 months or two independent sources; everything enters with `last_verified_at = null` and goes through moderation. Document this in `docs/data-provenance.md`.
- **Seed pins:** at approval, the moderator looks up the address with the existing Google autocomplete (T21) and confirms/adjusts the pin by hand; provenance stays `autocomplete:<place_id>` so T23 can later detect closures.
- **Taco types for seeded stands:** seed without taco types; users propose them (T44). With a taco-type filter active, stands without approved types are hidden; with no filter, all are shown.
- **Photos:** stand photos are pre-moderated; review photos keep post-moderation (hide after the fact); profile photos use automated review (below). Uploaders confirm they took the photo.
- **Profile photo:** optional; it replaces the app avatar immediately and then goes through an automated review pipeline (no manual queue). If the automated check rejects it, the app avatar comes back and the user is told why. The app avatar shows whenever there is no photo. Only shown next to visible reviews; never email.
- **Map/search area:** no hard geographic cap; coverage is the Monterrey metro area and its surroundings, and proximity only ranks results. The map loads pins for the visible region as the user moves, never the whole dataset at once.
- **"Comments"** are the review body; no separate comment threads (messaging is out of v1 scope).
- **Autocomplete scope:** map/search autocomplete only suggests stands and neighborhoods already in Taco Hunt (no Google calls). Proposing a new stand keeps Google autocomplete (T21).

### UI-first rule (owner decision 2026-09-29)

**Design/UI tasks block every other task.** The whole UI is finished first so the API is shaped by the UI, not the other way around:

- **Phase A (UI)** builds every screen and state from `docs/design-owner-feedback.md` in the mobile app. Phase A tasks may call endpoints that already exist, unchanged; anything new is served by typed fixture adapters in `apps/mobile/src/data/`. They must not touch `apps/api`, `packages/contracts`, or `supabase/migrations`. Each Phase A PR lists its **Data needs** (fields, states, endpoints) in its description.
- **Phase B (API)** starts only when **every** Phase A task is merged. It opens with T51, which turns the collected Data needs into the contract; each API task then implements its part and swaps the matching fixture adapter for the real call.
- Nothing else in the plan (including data work such as T43) starts before Phase A is complete. **Single owner-approved exception:** T31 (the one-line review-posting 503 fix) runs now, so reviews work while the UI is built and T36 can be tested end to end.
